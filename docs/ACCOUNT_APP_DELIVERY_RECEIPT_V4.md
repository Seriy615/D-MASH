# Account application delivery receipt V4 candidate

An ordinary Account text operation remains `PENDING` in encrypted sender history and encrypted sender outbox until a recipient-generated `ACCOUNT_APP_ACK_V4` frame authenticates under the confirmed N4 root. The receipt binds the Account pair, binding digest and generation, session ID and generation, content operation ID, and the exact application frame digest. A separate HKDF domain derives its AEAD key. A Node queue result is never a delivery receipt.

The recipient persists authenticated text history before emitting an ACK. Repeated exact application frames are checked against the same history marker and produce fresh ACK frames. The sender's `persistOutgoingAck` callback must atomically verify the outbound history marker and mark the existing message `DELIVERED`; only then does AppCipher persist `recipientAck` and Outbox replace encrypted plaintext intent with an encrypted tombstone while removing it from the pending index. A failed callback or deleted/mismatched history leaves the pending intent intact.

Each outbox retry first reserves a monotonic attempt in encrypted IndexedDB state. The Account application frame remains byte-identical; attempts after the first use a new HMAC-derived transport operation ID, causing `AccountSealedOperationV4` to create a new opaque recipient packet. This lets a recipient Inbox with a `seen` tombstone for the previous packet receive a bounded-rate duplicate. Backoff is 5 seconds to 5 minutes; there is no attempt-count expiry. The same-grant Node path still requires a real transport/Inbox test.

The constructor integration requires trusted callbacks `persistAuthenticated`, `persistOutgoing`, and `persistOutgoingAck` from the Account history writer. The public runtime option name is `persistOutgoingAck`. This candidate does not migrate pending text across a changed confirmed session/binding, carry media bytes, or prove ordinary UI/deployed delivery. Those cases remain N4 gates.
