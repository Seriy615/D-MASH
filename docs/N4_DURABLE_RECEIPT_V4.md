# Durable Account application receipts (isolated N4 candidate)

An authenticated inbound text or CONTROL frame first commits the Account history or CONTROL dispatch journal. AppCipher then stores the exact encrypted receipt frame in its owner-scoped `pairing_material` ledger and adds its operation ID to an encrypted pending receipt index. Only after both writes finish does `receiveApplication` return `persisted:true, ackStaged:true`. If the process stops between the two writes, the Node Inbox record remains unacknowledged and replay reconstructs the missing index. Existing Account identities, message rows, and keys are unchanged.

Network submission runs after the inbound result, so an offline sender cannot hold the current or next valid Inbox packet in the receipt send. A failed submission leaves the encrypted receipt pending across reload; the retry reuses its Account ciphertext with a fresh outer Node operation ID and bounded exponential backoff (5 seconds to 5 minutes). A successful local Node queue removes the pending index entry. A sender retry of the application frame can stage the same authenticated receipt again if the previous transport ACK was lost. Confirmed session successors do not submit an old-root receipt; the sender must resend its pending application under the new confirmed root.

The managed owner AbortSignal releases the Worker owner and cancels pending discovery; Node routing bounds discovery at 30 seconds. This change does not claim an independent per-receipt transport AbortSignal or successful recipient delivery from a local Node queue result. The red/green synthetic-IDB test covers an offline receipt send, processing a second valid inbound frame, and crash/reopen retry. A real Worker/Python/browser fault and cancellation gate remains required before integration.
