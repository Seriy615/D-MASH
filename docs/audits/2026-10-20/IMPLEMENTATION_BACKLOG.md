# Реализация: Android и Desktop одновременно

20 октября 2026. База анализа `9446c22f27309131456942870971d477f6f2358f`. Пользователь расширил поручение от плана до **работающего приложения с исправлением выявленных проблем** и выбрал параллельную разработку двух клиентов. Этот список — текущий переход к реализации; статусы не означают наличие готовых APK/desktop package.

## Правила приёмки

Общий portable runtime/transport contract; Android service и Desktop daemon принимаются независимо. Account plaintext/E2EE и полный DeviceRoot находятся вне сетевого daemon: credential broker передаёт только scoped transport bundle; legacy root-backed KEM authority явно учитывается. Same-UID/native/OS compromise не считается устранённым одним IPC. После durable handoff нет сетевых callbacks в Account. Никаких reset root/identities/history ради миграции или PASS, скрытого legacy fallback, production/deploy без отдельного авторизованного выпуска. Поддержанные требования N0–N8/A–M/E6 проверяются по существующему development plan, а не считаются выполненными из-за нового UI.

`ANALYSIS` — подтверждена проблема/спроектировано изменение; `SPIKE` — проверяется исполнимость; `TODO` — production code не исправлен; `FIXED` требует source diff и scoped regression; `ACCEPTED` требует независимого review и подходящего сквозного retest. В этом срезе **нет FIXED/ACCEPTED native функций**.

## Как проверять результат без подмены цели

Первый демонстрируемый результат — на **обеих платформах** чужой transit и собственная durable ciphertext очередь без Account login и без живого UI. Следующий — сообщения Android↔Desktop с закрытым sender Account после handoff, затем восстановление и обработка Inbox получателем. После этого self-organization/NAT и buffered files развивают тот же runtime, а Telegram UI использует его facade. Минимальный status UI не считается готовым обычным messenger UI.

Unit tests дополнены реальными browser/native actions. Перед новой разработкой инвентаризируются и проверяются все кнопки/меню/модальные controls и пользовательские flows текущего UI по `CURRENT_HANDOFF.md` §7; проверки повторяются после соответствующих fixes и перед full release, с BROWSER_QA/DEVICE_QA PASS/FAIL/NOT RUN, версиями page/SW/app, source hashes, первоначальными FAIL и retest. Destructive тесты — только synthetic profiles. Physical Android, настоящие NAT, installer и production не заменяются mocks.

Каждое исправление имеет reviewable diff, тест исходного failure, retained-state retest и отдельный статус. Неизвестных ошибок отсутствие не доказано; release блокируют известные критические дырки и недоказанные обязательные гарантии. Плановый snapshot и [независимый review](INDEPENDENT_REVIEW.md) не являются заявлением готовности приложения.
