# Expired CONTROL receipt reconciliation (isolated candidate)

An authenticated CONTROL frame can be replayed after its `expiresAt` if all transport receipts were lost. AppCipher still verifies the current Account session, AEAD additional data, canonical schema structure, operation ID, and exact ciphertext ledger context. It routes an expired frame only to the private `persistExpiredControl` callback. That callback must prove an exact previously durable **APPLIED** operation with the same peer, operation ID, type, payload and binding; it returns `{persisted:true, duplicate:true, expiredReplay:true}` before AppCipher stages an authenticated transport receipt. A new expired operation, a merely PENDING action, a changed type or payload, or a missing durable record is rejected without receipt.

The sender may retry only an operation already present in its encrypted AppCipher ledger. Same-session retry retains the exact Account ciphertext; a confirmed successor can reseal the same operation under the new root only after the existing branded successor proof and three-row SessionStore CAS. The receiver dispatcher needs the corresponding successor proof and three-row CAS before treating the fresh ciphertext as the old semantic action. No expiry is extended and no media action is executed by this receipt recovery path.

This slice is synthetic-IDB UNIT evidence only. The dispatcher callback and real Worker/Python/browser proof must be integrated and tested before activation. If the prior APPLIED journal record has been purged, recovery fails closed; durable retention horizon remains a protocol policy decision.
