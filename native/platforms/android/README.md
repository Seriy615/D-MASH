# Native Android Views and Node service

The launcher is a Java Views Activity. `NodeService` extends Qt's supported `QtService` host in an explicit separate `:node` process; no Activity, WebView or Account crypto is embedded in that process. The common actor, existing JS protocol resources, SQLite Inbox/jobs and bootstrap supervisor are linked into `libdmash_node_service_arm64-v8a.so`. `DMASH_HOST_EXTERNAL_APP` reuses the actual daemon entry with the service's existing QCoreApplication. The service entry uses Qt6.12’s `QAndroidService` CorePrivate wrapper so Qt’s service startup handshake completes before waiting for the broker descriptor.

The internal, unexported Binder descriptor `org.dmash.client.NodeBroker.v1`, transaction `FIRST_CALL_TRANSACTION`, accepts one ParcelFileDescriptor and a private profile path from the same app UID. The credential owner retains the other bootstrap socket endpoint/lifetime lease. JNI duplicates the supplied descriptor; the service receives only the strict scoped transport bundle over it. The native entry creates QCoreApplication before waiting for that handoff (15s limit), avoiding QtService startup waiting for a bootstrap that Java cannot yet supply. Missing handoff fails; the app invents no Node/Account identity or fake ready state.

Qt initializes/loaders and deployment resources are generated by `androiddeployqt`; Gradle uses Qt6.12's Android Gradle Plugin9.2.1, Gradle9.5.1, SDK36, JDK21 and NDKr27c from the permanent cache. Run `../scripts/build-android.sh` from the repository. CMake values control minSDK28/targetSDK36, rather than the manifest's deprecated uses-sdk attributes. OpenSSL shared libraries are explicit deployment inputs. Signing uses the disposable debug key only; this is not a release signature or reproducible release acceptance.

The foreground notification declares `specialUse` on Android14+ with an explicit manifest subtype for user-enabled continuous mesh routing/forwarding and a Stop Node action. Earlier Android versions use the ordinary foreground-service API. This selection follows the actual relay role; Android’s `remoteMessaging` description concerns continuity between a user’s devices, while `dataSync` is time-bounded transfer work. The declared special-use rationale still requires Google Play review for a Play release; it is not a bypass or proof of background availability. See [Android foreground-service types](https://developer.android.com/develop/background-work/services/fgs/service-types) and [timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout).

The notification starts before Qt initialization. Native startup failure/timeout and service stop write only a public status to an atomic app-private file, and the Activity queries a live Binder without starting a missing service. “Node service is running” confirms the live process/installed handoff only, not connected peers or delivery. `START_NOT_STICKY` avoids an unauthorized identity/credential restart. Stop/OS process death retains durable encrypted state. OS-wrapped scoped restart authority, reboot, permissions, Doze, network transitions and physical-device lifetime remain separate required gates. There is no boot receiver or battery-exemption request and no promise of unstoppable background transit.

The ordinary launcher now uses native Views for fresh profile creation, optional Account creation/sign-in, complete-profile import, contacts/history, Saved text, Node connections/start/stop and cancellation. Details → Node tools opens the separate technical diagnostic Activity. A separate unexported `:credentials` foreground service owns the shared credential host, Root and existing Account JS/WASM crypto; the UI uses framed local IPC. The `:node` service receives only the scoped transport grant. Closing or killing the UI process does not request Root lock. Stop Node and lock explicitly closes the Account session and fences the owned Node.

The Android adapter records the exact owned Node process identity before handoff, verifies prior-process exit during recovery, checks owner epoch separately from transport generation, and extends leases through private RenewCapabilityLease when supported. The ordinary UI reports actual host status; it does not treat a Java bind request or installed JNI descriptor as transport readiness.

The v5 x86 APK is compiled and package-verified: both native services, all 18 ELF objects aligned for 16K pages, min SDK28/target36, debug signature and dependency notices. Immutable package mapping is in `evidence/account-v5-checkpoint.json`. Runtime is NOT RUN for these new ordinary flows. Earlier diagnostic APK runtime failed before native ENTRY with Qt service state STARTING; bounded loader diagnostics remain necessary. No Android messaging or background lifetime PASS is inferred from compilation.

`ci-runtime.py` now requires actual fresh Root Cancel/empty/mismatch/create, optional Account cancellation, visible zero-Account Node start, UI-only process death/reconnect, visible Node stop/lock, actual Account creation/Saved write/reopen/signout, and the unchanged strict technical disabled-controls checks through Node tools. Separate same-UID scoped service instrumentation remains independent of ordinary Account transport. CI reports only reached checks; no retained profile import, remote chat, contacts/pairing, Doze or physical-device acceptance is claimed.

All platform source is original. Qt's LGPL/GPL/commercial terms and bundled dependencies keep their original notices; no Telegram resources/code are copied into this checkpoint. This directory does not alter the frozen audit/license requirements.
